# AppSelect second-tap reopen root cause

## User-visible symptom

On iOS, when a Radix `AppSelect` is already open, tapping the original trigger area again (including the chevron) appears to reopen the menu instead of closing it.

## Root cause

The first fix handled the `pointerdown`-time close but missed the follow-up `click` generated by the same touch gesture.

Sequence on iOS/WebKit:

1. Select is open and Radix's dismissable layer disables outside pointer events.
2. A second tap lands at the original trigger coordinates.
3. `onPointerDownOutside` recognizes that coordinate and closes the controlled Select.
4. Pointer events become available again after the close.
5. The same gesture then emits its trailing `click` on the trigger.
6. Radix Trigger is open-only, so that click requests `onOpenChange(true)` and reopens the menu.

This makes the close/reopen cycle look like the second tap did nothing.

## Fix

`AppSelect` now arms a short-lived one-shot reopen suppression only when an open Select is closed from `onPointerDownOutside` at the trigger coordinates. The trailing open request from the same gesture is consumed. Normal opening, item selection, keyboard navigation and outside-dismiss behavior are unchanged.

## Regression

A dedicated mobile browser regression explicitly reproduces the two-phase sequence: trigger-area `pointerdown` closes the open Select, then a trailing trigger `click` is dispatched and must not reopen it. This complements the existing screen-coordinate touch smoke test, which did not reproduce iOS's follow-up-click timing reliably in Playwright WebKit.
